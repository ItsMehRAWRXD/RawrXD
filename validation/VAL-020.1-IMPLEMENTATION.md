## Determinism Testing (G4)

### Triple Execution Protocol

```
Run A: input → block → output → hash(X)
Run B: input → block → output → hash(X)  
Run C: input → block → output → hash(X)

PASS if: hash(A) == hash(B) == hash(C)
```

### Cross-Backend Determinism (Future)

```
NativeBackend:    hash(X)
VulkanBackend:    hash(X)  ← must match
ROCmBackend:      hash(X)  ← must match
```

## Key Design Decisions

### 1. Immutable Baselines
VAL-020.1 consumes VAL-019 baselines as fixtures. No regeneration.

### 2. Intermediate Tensor Capture
Every tensor between kernels is hashed and recorded. Essential for debugging composition failures.

### 3. Topology as Evidence
Execution graph is part of the evidence, not just inputs/outputs.

### 4. Hardware Fingerprinting
Evidence includes CPU features, GPU model, driver version for reproducibility.

### 5. Triple-Run Determinism
G4 requires 3 identical executions, not just 2.

## Risk Mitigation

| Risk | Mitigation |
|------|------------|
| QKV layout mismatch | Tensor manifest captures shape/strides |
| RoPE offset errors | Position tensor in manifest |
| KV cache corruption | Cache state hashed after each update |
| Residual drift | Intermediate residual tensors captured |
| Backend nondeterminism | Triple-run + hardware fingerprint |
