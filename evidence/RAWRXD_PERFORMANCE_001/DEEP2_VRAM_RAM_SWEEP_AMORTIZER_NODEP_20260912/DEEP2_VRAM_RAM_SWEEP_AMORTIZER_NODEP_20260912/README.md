# Deep2 VRAM/RAM Sweep Amortizer — no dependencies

Purpose
-------
Break the strict "one dense target-weight sweep per emitted token" execution shape without changing the target model.

This drop does NOT claim that a dense transformer's weights can be used without being read by the GPU.
Instead it changes the unit of work:

    old: 1 target sweep -> 1 token
    new: 1 target sweep -> verify N draft positions -> accept 1..N (+ optional bonus) tokens

The target model remains authoritative.  In exact greedy mode, a draft token is accepted only when it
equals the target model's greedy token for that position.  At the first mismatch, the target token is
emitted instead.  If the entire window matches, the target's bonus token may be emitted.

This makes "accepted tokens per target sweep" a first-class performance metric and permits each target
weight tile to be reused across multiple positions inside the verification batch.

Intended hardware mapping
-------------------------
For a ~25 GB dense target that fits in a 32 GB GPU:

    GPU0 / R9700 32 GB:
        target weights resident for the whole generation
        target KV
        verification scratch KV
        activation/scratch arena

    GPU1 / RX 7800 XT 16 GB:
        draft model + draft KV
        draft generation runs concurrently where the runtime permits

    system RAM:
        mmap/backing image, recovery, cold assets
        NOT part of the steady-state target token loop

For targets larger than one GPU, the same scheduler still applies.  The target verifier can be backed by
Deep2 tensor-parallel, layer-resident, or exact-range streaming execution.  The key invariant is that one
verification pass processes multiple candidate positions while a weight tile is resident in the kernel.

No third-party dependencies
---------------------------
The library is C++17 and uses only the C/C++ runtime.  It does not include Vulkan, llama.cpp, Ollama, CUDA,
ROCm, or any external SDK.  Deep2 binds its already-existing GPU runtime through function pointers.

Deep2 binding contract
----------------------
The target verifier callback MUST:
  1. use the currently committed target KV as its base state;
  2. evaluate the proposed candidate window in one target verification transaction;
  3. return target greedy tokens aligned to every candidate position plus one bonus token;
  4. keep candidate KV writes speculative until finalize_verify();
  5. on finalize_verify(prefix_count), commit only the KV generated by the accepted candidate prefix;
  6. on abort_verify(), discard all speculative KV writes.

The emitted mismatch/bonus token does not need KV until it is consumed as input by the next verification
cycle.  That matches normal autoregressive decode semantics.

Critical steady-state invariants
--------------------------------
TARGET_WEIGHT_RESIDENT=1        for models that fit target VRAM
RAM_TO_VRAM_PER_TOKEN=0         after load/warmup
HOST_LOGITS_PER_TOKEN=0         target verifier should reduce on device
TARGET_SWEEPS < GENERATED_TOKENS whenever average accepted tokens/sweep > 1
VERIFY_WINDOW >= 2              after the controller has demonstrated useful acceptance
TARGET_AUTHORITY=1              draft never promotes a token without target verification

Important boundary
------------------
This design removes RAM/PCIe from the steady token loop when target weights fit in VRAM, and can amortize
VRAM weight traffic across several accepted positions.  It does not repeal the need for the target GPU to
read dense weights during a target verification sweep.
