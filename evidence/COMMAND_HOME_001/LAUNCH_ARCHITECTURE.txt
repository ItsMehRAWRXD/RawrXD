Largest local model (honest, public-safe path)
----------------------------------------------
Use existing Deep2/GGUF + AgenticBridge in Win32IDE — NOT a second demo exe.
- Scan/load via ScreenPilotModelHub (F:\OllamaModels, browse .gguf)
- ~7B–13B: full VRAM on R9700 32GB with headroom for KV
- ~32B Q4_K_M: primary dense lane (~20–28 GB VRAM); one active stream
- 70B+ Q4: hybrid GPU+RAM offload; throughput drops; not multi-tenant SaaS
- Continuous batching may raise aggregate TPS for YOU locally; per-stream
  latency still bounded by memory bandwidth — no inverse scaling claim
- In-tree tensor "slingshot" (GGUFShardRouter) = shard prefetch, NOT UI fiction

Concurrency & performance (correct physics)
-------------------------------------------
Continuous batching CAN raise aggregate tokens/sec on one GPU by multiplexing
requests into shared KV/scheduling windows. It CANNOT make per-user latency
improve indefinitely:
  - Low concurrency: latency dominated by prefill + decode for one stream
  - Saturation: queue depth grows; each user waits longer (plateau then degrade)
  - VRAM: second large model or context can OOM or force swap/throttle
Marketing must say "efficient local batching when YOU run multiple tasks"
not "more remote users makes everyone faster."

MASM multiplex sample — classification
--------------------------------------
The ring-buffer / LOCK CMPXCHG sketch is a busy-loop prototype only.
It is NOT a shippable remote steering stack. Missing before any exposure:
  - Winsock accept loop bound to 127.0.0.1 (or paired tunnel only)
  - HTTP/TLS (Schannel) or equivalent authenticated framing
  - Pairing, session tokens, capability scopes, approval replay
  - Model bridge into Deep2 with cancellation + shutdown
  - Safe teardown, backpressure, audit journal hooks
"No third-party runtime" ≠ "no OS facilities." A secure Windows service still
uses kernel32/ntdll, Winsock, Schannel (or self-built crypto — not recommended).
