# ---- Model-Size Alpha Convention (corrected from DEEP2_EMPIRICAL_SCALING_AUTHORITY_002) ----
# For positive slowdown-exponent convention:
#   TPS ∝ SIZE^-α
#   α = -ln(TPS_X) / ln(SIZE_X)
# Valid only when:
#   SIZE_X != 1 (distinct model bytes, not just nominal vs active)
#   MODEL_BYTES_A = exact measured file lengths, not approximate nominal values
#   MODEL_BYTES_B = exact measured file lengths
#   same execution policy
#   same agent count
#   same workload policy
#   raw timing authority exists
# If SIZE_X == 1 (same model), the result is implementation scaling, not model scaling
# If any valid condition fails: ALPHA=UNDEFINED
#
# Do not mix with signed slope ln(TPS_X)/ln(SIZE_X) convention.
# If you want a positive model-size slowdown exponent, use:
#   TPS ∝ SIZE^-α
#   α = -ln(TPS_B / TPS_A) / ln(SIZE_B / SIZE_A)
# rather than mixing that convention with the signed slope.

# ---- Beacon Transfer Rule ----
# Do not transfer the complete model or complete KV cache on every token.
# Preferred structure: persistent model/state replica + per-token mutable delta
# + control beacon
# Conceptually: GPU A computes token N --> token ID + KV append + mutable state
# delta --> BEACON --> GPU B computes token N+1
# For hardware without direct peer access:
#   GPU A --> GPU DMA --> pinned host-visible staging --> GPU DMA --> GPU B

# ---- Token-State Coherency ----
# Every mutable state dependency between token turns must be identified.
# At minimum: TOKEN_ID, POSITION, ROPE_POSITION, KV_APPEND, KV_EPOCH,
# SAMPLER_RNG_STATE, SAMPLING_HISTORY, PENALTY_STATE, GRAMMAR_STATE,
# SPECULATION_STATE, MOE_ROUTING_STATE, EXPERT_CACHE_GENERATION,
# WINDOW_STATE, ATTENTION_SINK_STATE, CACHE_EVICTION_GENERATION
# A token flip is not valid until the next hardware owner has authoritative
# state for every required mutable dependency.

# ---- Five Core Scaling Axes Summary ----
# AXIS_1 = MODEL_SCALING        — distinct exact model-size scaling (α when SIZE_X != 1)
# AXIS_2 = IMPLEMENTATION_SCALING — same model, different engine/config (this experiment)
#   PRIMARY: IMPLEMENTATION_GAIN = TPS_NEW / TPS_BASELINE
# AXIS_3 = CONCURRENCY_SCALING  — genuine simultaneous-stream scaling (AGENT_COUNT=1,2,3...)
#   Primary: WALL_GAIN_N = WALL_AGGREGATE_TPS_N / WALL_AGGREGATE_TPS_1
# AXIS_4 = RESIDENCY_SCALING    — physical/effective working-set scaling
#   Derived: RESIDENCY_RATIO = PHYSICAL_WORKING_SET_BYTES / MODEL_BYTES
# AXIS_5 = SWARM_HEX_MAG_SCALING — orchestration rather than simultaneous inference
#   Derived: USEFUL_WORK_PER_SEC, USEFUL_SWARM_TPS, DUPLICATE_WORK_RATIO, etc.
#
# Token Beacon Ferris sits under Axis 2 + PLACEMENT_AUTHORITY, NOT as a 6th axis.
# Hex Mag = orchestration scaling (Axis 5)
# Token Beacon Ferris = execution/placement implementation (Axis 2)
# Concurrency = simultaneous-stream scaling (Axis 3)
# Residency = physical/effective working-set scaling (Axis 4)
# Model scaling = distinct exact model-size scaling (Axis 1)

# ---- Asymmetric GPU adjustment ----
# GPUs are asymmetric: R9700 (32GB) + 7800 XT (16GB)
# Generalized beacon wheel should support weighted ownership:
#   A A B
#   A A B
#   A A A B
#   A A A B
# Dynamic form: A A B A A A B A ...
# based on measured hardware service time.
# Controller learns:
#   R9700 median token service = X
#   7800XT median token service = Y
# and adjusts slot ownership accordingly.

# ---- MoE version (future work) ----
# For MoE, the beacon can include router information:
# TOKEN_ID, POSITION, KV_EPOCH, TOP_EXPERT_0..3, EXPERT_CACHE_GENERATION
# Then the device receiving the next turn knows what happened and can update
# its expert predictor/cache.

# ---- Bigger-model version ----
# Instead of requiring every byte on both devices:
#               SYSTEM RAM
#                   │
#             backing weights
#                   │
#          ┌────────┴────────┐
#          ▼                 ▼
#     R9700 HOT SET      7800 HOT SET
#       32 GB              16 GB
#          │                 │
#          └──── BEACON ─────┘
#
# During A's turn: A = token engine, B = predicts/prepares/caches next likely working set
# During B's turn: B = token engine, A = predicts/prepares/caches next likely working set
# Now the ferris wheel includes cache preparation, not merely compute alternation.
# That has a much stronger chance of creating useful overlap.

# ---- One hard requirement ----
# For true ABAB token execution, the hardware about to receive ownership must possess
# everything required to execute that token.
# That means either: A = complete required weights, B = complete required weights
# or some mechanism giving B access to weights it doesn't locally contain.
# This is why the idea is easiest to prove first with a model fitting independently
# on both devices. Your 7800 XT's 16 GB is therefore the immediate constraint for
# the literal replicated-model version.
# For models larger than that, evolve into:
# BEACON FERRIS + expert/weight cache + selective replication + remote backing store
# rather than abandoning the concept.
